# 任务 4：长对话结构化记忆设计

日期：2026-10-10。状态：已按确认方案实现，验证结果及边界见 [task-4.md](task-4.md)。

## 目标与范围

让工作流文本 AI 节点在早期消息退出历史窗口后，仍能使用用户明确给出的目标、预算和约束。用户更正必须在下一次开始的回答中生效；不确定事实需要澄清；事实及其变化能回查原话。清除记忆不删除聊天记录。

首版只支持应用工作流中的一个顶层、无工具、无多模态的文本 AI 节点启用记忆；发布校验拒绝多个记忆写入节点、循环内记忆节点及其他运行模式。其他节点保持现有行为。调试会话使用独立临时状态，不写入正式会话记忆；刷新或缓存过期后允许丢失，界面明确提示。普通问答管线、跨会话记忆和工具恢复不在本次范围。

新配置默认关闭，跟随现有工作流版本保存，不修改已发布应用。没有记忆的旧会话可以直接聊天；首次启用只处理新消息，不自动扫描全部旧历史。

## 已核对的上游接口

- `apps/application/models/application_chat.py`：`Chat` 记录应用和会话所有者；`ChatRecord` 保存用户问题、答案和节点详情。
- `apps/chat/serializers/chat.py`：工作流请求携带 `chat_id`、`chat_record_id`、当前用户原话及身份；恢复缓存时只读取最近 5 条记录。
- `apps/application/flow/step_node/ai_chat_step_node/impl/base_chat_node.py`：生成提示后组装历史与模型消息，任务 3 的轻量上下文在此执行。
- `apps/application/flow/i_step_node.py`：回答完成后保存聊天记录及汇总用量。因此记忆更新不能依赖当前 `ChatRecord` 已存在。
- 上游 `ApplicationLongTermMemory` 按应用和用户存储摘要，`application/long_term_memory` 可跨会话提取，开始节点暴露 `memory` 变量。它缺少本任务需要的会话隔离、逐条来源及变更状态，不视为本任务已完成。

上游长期记忆继续保持原语义，但启用本策略的节点不得同时在系统提示或问题模板引用上游 `memory` 变量；配置校验给出错误，避免两套记忆产生冲突。任务 3 的轻量上下文可同时启用，先执行它的来源校验和去重，再执行本任务的消息预算选择。

## 方案选择

采用“结构化事实记录＋受约束模型提取”。纯规则便宜、可重复，但难以覆盖开放表达；整段摘要接入简单，但无法可靠定位单条纠正和来源。提取模型只提出候选操作，由服务校验、合并及保存，不直接执行数据库更新。

使用节点当前已解析且授权的文本模型做一次非流式提取，复用现有供应商抽象；不增加供应商接口或单独模型路由。提取是额外调用，必须单独计量。提取模型参数与提示版本进入运行轨迹，服务商支持时使用结构化输出，否则解析严格 JSON；不因格式错误自动重试。

## 数据与状态

新增两个独立表，不把记忆写入可能被工作流变量覆盖的 `Chat.meta`：

1. `ConversationMemory`：一条记录对应一个 `Chat`，包含递增 `version`、`generation`（清除代次）、事实快照、更新时间。通过 Chat 关联应用和所有者，删除 Chat 时级联删除。
2. `ConversationMemoryEvent`：追加式事件，保存操作类型、前后版本、代次、请求标识、来源轮次 UUID、来源类型、用户原话快照、原话哈希、候选操作及实际变更。状态写入与事件追加处于同一短事务。

事实结构：稳定 `fact_id`、事实键（实体／属性）、值、状态、来源事件与轮次、引用原文、版本、更新时间。状态为 `confirmed`（用户明确陈述）、`pending`（待确认）、`superseded`（被更正）、`revoked`（撤销）；“已确认”不代表模型或外部资料验证为真。值与引用设置长度上限，快照最多 100 条有效或待确认事实；达到上限时保留现状并报告容量不足，不静默删除条件。

当前用户消息在模型回答前保存为事件中的原话快照，使用工作流已经分配的轮次 UUID。此时来源标记为“本轮用户消息”；回答落库后可关联 ChatRecord。回答失败仍可追溯已经接收的用户原话，不能虚构已完成聊天记录。来源查询始终限定当前 Chat，不使用仅凭全局记录 UUID 的回查。

手工纠正来源标为“用户在记忆面板修改”，保存操作身份和时间，不伪造聊天轮次。原有 ChatRecord 可能在重新生成时被更新，因此来源引用保留写入时的不可变原话快照。

## 更新流程与冲突

1. 验证应用、会话所有者、客户端类型及会话未逻辑删除；取得状态版本和代次。
2. 保存当前原话来源；读取当前有效事实和有限历史证据，构造提取输入。输入中不含检索资料、工作流拼接提示和模型密钥。
3. 模型返回 `add`、`replace`、`revoke` 或 `pending` 操作，以及引用原文、目标事实 ID 和原因。新增事实只能来自当前用户明确表达；历史回答只能作为指代对象的证据，不能自动转成用户事实。
4. 校验字段、长度、目标归属和引用原文确实存在。引用存在只证明来源位置，不证明语义正确；无法证明是明确更正或撤销时降为待确认。
5. 通过版本及代次条件更新保存快照和事件。模型调用不持有数据库锁。发现并发变更则丢弃旧提取结果、重新读状态，不重复外部调用；本轮进入保守上下文模式，下一轮再正常提取。
6. 合并完成后选取记忆并调用回答模型；每次回答开始前重新确认版本没有被面板纠正或清除。已开始流式输出的回答不追溯改写，后续请求使用新状态。

明确更正如“预算从 3000 改为 4000”：旧值变为 superseded，新值为 confirmed，事件保留前后值与来源。没有明确覆盖意图的矛盾陈述：保留两个版本并标记冲突，回答上下文只发送冲突说明和必要原文，要求澄清，不能任选一个旧值作为条件。

“不再要求防水”产生撤销记录；撤销条件不再进入有效事实区。待确认候选不能自动替代 confirmed。面板纠正优先于发生在它之前的提取结果；用户在后续轮次的明确更正仍可改变面板值。

同一轮次 UUID、消息哈希及代次的重复处理不重复提取、不重复新增事实。重新生成相同用户消息可重新回答，但复用事实更新结果。首版启用记忆后拒绝修改既有轮次原话的重答请求，提示作为新消息发送，避免历史分支与后续记忆混合。

## 指代回查与上下文预算

提取前总是提供近期原始消息；对“第二款”“那个方案”等显式指代，再按本会话轮次顺序回查原始 ChatRecord，最多回查 20 轮，并受统一提取预算约束。可根据现有事实来源直接定位更早的原话。历史按稳定时间及 UUID 排序，不以缓存长度计算全局轮次。

历史答案可证明当时列举的顺序；只有能唯一关联当前用户表达时才确认对象。多个候选或记录缺失时保存 pending，回答要求澄清。首版不宣称能解析任意指代，不做跨会话或全库语义检索。

节点配置建议默认值：记忆及近期历史预算 2048 token、提取输入预算 4096 token、提取输出上限 1024 token、超时 20 秒；近期轮数沿用 `dialogue_number`。这些是实现默认值，不是评测调参结论。

回答模型的系统提示和当前用户问题不属于上述 2048 token 的历史预算，不能截断用户本轮输入来伪装达标。总输入仍须符合模型上下文容量，无法容纳当前输入时沿用明确错误路径。

确定性选择顺序：本轮更正／撤销／冲突说明，最新完整原始问答轮次，本轮提及实体关联的有效事实，其余近期消息及按更新时间排序的有效事实。实体关联使用规范化键／别名匹配，未匹配时回退到最近事实；不能宣称穷尽语义相关性。整条事实及整轮消息选择，不截断为残缺条件。无法容纳必要冲突证据时不使用该事实，输出澄清指引。

使用现有模型 tokenizer 计算预算；不可用时采用明确标注的保守估算，并记录计数方式。估计预算不是服务商实测 token。记忆作为单独标记的对话数据块传入，系统提示说明它是用户提供的上下文，不能覆盖系统规则；禁止将用户原话直接拼成系统指令。

轨迹保存所选事实 ID／版本、来源、排除原因、实际发送的历史及记忆块、预算计数与提取状态。模型实际输入测试对照这些字段，不能仅测试中间选择函数。

## 失败、清除和隔离

提取超时、JSON 错误、引用无效或用量缺失都显式记录。失败不改写已有事实；本轮禁用未核对的记忆注入，保留当前原话及预算内近期历史，并提示模型无法确认的旧条件应澄清。回答调用可以继续，不因提取失败伪造成功记忆。

清除在事务中移除事实快照和包含记忆内容的旧事件，递增 generation，保留不含事实值的清除审计事件。ChatRecord 及已有回答轨迹保留；界面明确“仅清除记忆，不删除聊天记录及历史执行详情”。在清除前启动的提取不能写回。首次启用和清除后均记录回查起点，不能自动从起点以前的原话恢复旧事实；用户重新明确表达才可重新记住。

关闭策略停止读取、更新及额外模型调用，但不删除已有记忆；重新开启时可继续使用，界面提示该行为。清除与关闭为两个独立操作。

## API 与界面

聊天端新增 `GET /chat/api/chat_memory/{chat_id}`、`PATCH /chat/api/chat_memory/{chat_id}/facts/{fact_id}`、`DELETE /chat/api/chat_memory/{chat_id}`。PATCH 支持纠正、确认和撤销，客户端提交 expected_version；版本冲突返回 409 并要求刷新。DELETE 同样校验版本。写操作携带请求 UUID，防止重复点击产生重复事件。

沿用 ChatTokenAuth，从认证上下文获得身份，不接受请求体覆盖应用或所有者。所有读取、来源回查、写入均同时约束 application_id、chat_user_id、chat_user_type 和有效 Chat。不存在及越权统一返回不可访问，不泄露事实内容。调试入口沿用工作流编辑权限，单独读取临时态；分享链接不授予记忆读写权限。应用 API key 保持现有应用身份边界，不宣称区分共享同一 key 的最终用户。

共享聊天组件增加“会话记忆”面板，桌面、移动和嵌入聊天复用：显示事实、状态、来源原话／轮次、更新时间；提供纠正、确认、撤销及清除。清除前说明保留聊天记录的语义。AI 节点配置增加开关及预算参数，执行详情增加记忆选择、变更和提取用量。普通用户面板不展示其他用户数据、系统提示或完整供应商请求。

## 计量与验证

提取和回答分别记录 provider/model、提示版本、输入／输出用量、耗时、错误、价格快照和费用。只有已取得两次实际计量时才汇总；任一缺失则总用量／费用标未知，不让原有默认零掩盖缺失。保留与上游节点统计兼容的字段，评测读取新增分项明细防止双计数。若既有长期记忆异步提取开启，也必须纳入评测费用；受控对照默认关闭它。

先写可失败行为测试，再实现：

- 事实新增、更正、含糊冲突、撤销、面板修正下一轮生效；3000→4000、第二款及撤销防水要求。
- 来源伪造、跨会话 UUID、不同客户端类型、逻辑删除、分享权限；缓存过期后仍可读记忆和回查。
- 幂等重复、并发改动、清除时提取仍在运行、重新生成及旧原话不复活。
- 超预算、末尾关键事实、tokenizer 不可用、提取超时／格式错误、缺失计量。
- 默认关闭无额外调用且原消息不变；任务 3 顺序、工具／多模态／循环配置拒绝；流式和非流式实际消息及用量轨迹。
- UI 查看来源、修正／清除、版本冲突；迁移、目标 Django 测试、相关任务 2/3 回归、局部 Ruff/ESLint、Vue 类型检查及两种 SPA 构建。

多轮开发集用于调试，另封存未参与调参的长对话验收题。固定模型与提示配置对照原历史策略和记忆策略，题目跨度须超过历史窗口。记录多轮正确率、遗漏和错误继承次数、总输入 token、总费用及耗时，逐题保留失败。用户更正场景必须全部通过人工复核，不能仅凭提取模型输出判断成功；总体质量不得因压缩下降。真实调用沿用已有预算控制机制，实账未知时不得宣称省钱。

任务 3 第二版仍缺正式人工质量评分、完整 HTTP/工作流端到端验证，本设计保留该前置限制。用户已要求启动任务 4，允许独立设计与开发，但最终报告不能宣称全部阶段完成验收。
