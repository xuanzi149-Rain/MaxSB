# MaxKB v2 二次开发实施任务

## 使用说明

**当前状态：**本文最初编写时尚未检出源码；以下仍保留原实施任务与验收协议。2026-10-10 的实际完成、验收、GitHub 和本机隔离部署状态以 [任务 1–5 闭环记录](implementation/acceptance-deployment-closure.md) 为准，不能把原计划文字当作当前进度。

**最终目标：**&#x57FA;于固定的 MaxKB v2 提交，完成六项可演示的增量改进，并用同一题集比较原版与改版。面向 Agent 应用开发实习岗位，重点证明 Python/Django 后端、Vue 前端联调、RAG、工具、状态管理、模型接入和评测能力。

**任务顺序：**&#x4EFB;务 0 环境与源码 → 任务 1 评测基线 → 任务 2 上下文去重 → 任务 3 动态检索 → 任务 4 会话记忆 → 任务 5 工具恢复 → 任务 6 模型路由。每项都在上一项验收后开始。任务 1 对应原计划第 6 项改动；其余名称与原计划一致。

**统一度量：**&#x56FA;定同一上游提交、知识库快照、问题集、模型版本、提示词、模型参数和运行环境。记录每题输入/输出 token、实际 API 费用、总耗时、检索证据、最终答案、引用、节点轨迹和错误。正确率由预先写好的关键事实与人工复核判定；P95 按单题总耗时计算。成本按模型服务商当次价目与实际用量计算，不能凭 token 数宣称省钱。涉及模型路由时，报告两个模型的合计费用。每项优化都同时检查质量与成本，不能只展示有利指标。

**题集：**&#x5148;建 20 题开发集供调试，再建 80 题冻结验收集。至少覆盖简单直答、多段证据、重复段落、无相关资料、长对话指代、工具成功/超时、资料冲突和模型路由。题目、公开资料、预期事实、必需证据标识与判分规则以版本化文件保存。冻结集在最终对照前不用于调参。真实模型 API、密钥和费用预算由实施者配置；密钥仅放本地环境变量或密钥管理中，不进入仓库。

**开发约定：**&#x68C0;出源码后先读仓库根目录 `AGENTS.md`、子目录约定和 `.github/workflows/`。保持上游工作流及发布任务，新增检查仅在现有 CI 不能覆盖新代码时添加。上游说明当前采用 `python main.py` 入口、Python 3.11/Django、Vue 3，前端类型检查为 `npm run type-check`；这些命令须在固定提交再次核实。不要运行会自动改写整个仓库的 lint 命令来做只读检查。每项改动先写能失败的行为测试，再实现、跑目标测试与相关回归测试，最后记录通过证据。[上游开发说明](https://github.com/1Panel-dev/MaxKB/blob/v2/AGENTS.md)

## 任务 0：固定源码并跑通原版

### 通俗解释

先把“原装机器”放到桌面，记录它的出厂编号并试运行。以后才能说清楚哪些能力原来就有，哪些是自己改出来的。

### 具体步骤

1. 将 MaxKB v2 完整 Git 仓库检出到本项目工作目录；若当前目录已有本文档，先确保文档被保留。记录上游远端、提交 SHA、检出日期和本地分支。不要只依据浮动的 `v2` 分支名复现实验。
2. 阅读实际检出的 `AGENTS.md`、相关目录约定、`README`、开发依赖及 `.github/workflows/`。列出原版已有的知识检索、模型选择、工具重试、会话历史、评测或命中测试功能，划清增量改动边界。
3. 按该提交的官方开发方式启动数据库、Redis、后端、异步任务及 Vue 管理界面。创建一份公开知识库、一个问答应用、两个可用模型配置和一个只读测试工具。不要把 API 密钥写入文档或提交。
4. 手工走通“上传资料 → 提问 → 检索 → 模型回答”和“工作流调用工具”两条路径，保存不含凭据的启动命令、截图/日志和故障记录。
5. 建立 `docs/implementation/evidence/` 的记录格式：提交 SHA、环境、测试命令、结果及已知限制。保留上游原始行为的对照运行记录。

### 验证与完成条件

- `git rev-parse HEAD` 得到固定 SHA，且能指出当前分支与上游远端。
- 后端、前端与所需服务启动；网页能完成一次知识问答和一次工具调用。若机器或 API 条件不足，记录明确的阻碍，不把“启动命令写好了”视为通过。
- 对应版本的 Python 检查、前端类型检查与构建命令实际运行，保存退出码和失败清单。
- 输出一份“上游已有功能/计划新增功能”对照，后续任务据此避免重复开发。

## 任务 1：评测基线与版本对照（原计划改动 6）

### 通俗解释

给系统准备一套固定考卷和计分表。每次改代码后都答同一套题，才能知道它是更好、更便宜，还是只是换了一种说法。

### 具体步骤

1. 在现有应用/聊天接口上确定批量提问入口、流式响应聚合方式以及 token、引用、节点详情和错误的来源。画出一题从发起到保存结果的数据流。
2. 定义版本化题目结构：题目 ID、场景、输入轮次、公开文档及证据 ID、预期关键事实、可接受答案、所需工具行为和判分规则。先写 20 题开发集，再封存 80 题验收集；数据不得含个人隐私。
3. 实现后端批量运行服务。每题独立执行并持久化 `run_id`、代码 SHA、应用/工作流版本、模型配置快照、答案、引用、节点轨迹、输入/输出 token、实际费用、耗时、错误与判分结果。单题失败不能中断整个批次；重复运行必须生成新 `run_id`。
4. 建立管理 API：创建运行、查询进度、查看题目详情、比较两个已完成运行。沿用上游认证和权限规则。报告页展示汇总指标、逐题差异和可展开的失败轨迹；不向普通用户展示模型密钥或敏感工具参数。
5. 用原版固定提交运行两次开发集，检查相同配置下结果是否可复现；记录模型随机性造成的差异。随后只运行一次冻结集作为原版基线，并保存原始结果。

### 验证与完成条件

- 行为测试覆盖批量成功、单题失败后继续、重复运行不覆盖、权限隔离、流式结果聚合及缺失 token 数据的标记。缺失计量显示为“未知”，不能当作零。
- 页面能比较两个 `run_id`：正确率、证据召回率、引用准确率、工具任务完成率、平均输入/输出 token、每成功任务费用、P95 耗时，以及逐题失败原因。
- 至少有一次真实模型运行；报告内的 SHA、数据集版本、模型版本和时间可追溯。人工评分项标明复核人和规则，不把模型自评分当作事实。

## 任务 2：检索上下文去重与证据保留（原计划改动 5）

### 通俗解释

检索像从书架上拿资料。五张纸若有三张写着同一件事，就只带必要的纸给模型；但每张保留的纸仍要知道来自哪本书、哪一页。

### 具体步骤

1. 找到现有检索节点输出、重排结果以及模型节点接收证据的接口。先确定是否已有去重、截断和来源字段；只在缺口处加处理器。
2. 定义可配置的上下文预算和去重阈值。首版使用确定性规则：规范化文本、识别完全重复和高重合片段；在相似片段中优先保留相关性更高且来源完整的一条。若无可靠相关性分数，仅去重与按原排序截断，不臆测“无关”。
3. 处理器输出保留片段、删除原因、原始片段到保留片段的映射及估计 token。引用仍指向真实文档/段落，不生成不存在的来源。
4. 在节点详情中显示原始/保留片段数、估计节省 token、被排除的证据及原因。默认关闭新策略，便于同一工作流切换原版与改版；配置跟随现有应用版本保存。
5. 用任务 1 的同一题集比较。若预先标注的必需证据被删、引用准确率下降或回答关键事实错误，归为质量回归并分析阈值。

### 验证与完成条件

- 单元测试覆盖重复、近重复、不同来源同内容、空结果、超预算及关键证据位于末尾。测试明确断言来源映射和原始证据 ID。
- 集成测试证明关闭策略时行为与上游一致；开启后模型实际收到的是处理后的证据。
- 报告同时列出 token、正确率、必需证据保留率、引用准确率和耗时；不能只以 token 下降宣布完成。

## 任务 3：动态检索预算（原计划改动 1）

### 通俗解释

问“你好”不用翻资料；问“比较两项方案的条件”可能要翻更多页。系统先判断问题需要多少资料，再按这个决定去查。

### 具体步骤

1. 识别当前知识检索节点的 `top_k`、相似度阈值、重排开关与执行入口；确认配置如何序列化、校验和展示。
2. 首版使用可解释的规则分类：寒暄/无需资料、单事实问题、多条件或比较问题。给每类配置检索开关、候选片段上限和重排策略；无法明确分类时使用原有固定配置，不自行臆断。
3. 将决策放在检索调用之前，并把决策原因、最终参数、原始命中和送入模型的证据写入节点详情。与任务 2 串联时，先决定检索规模，再去重和控制上下文。
4. 增加工作流配置项与管理界面说明；默认关闭，旧工作流无需迁移即可运行。若上游已有等价能力，应改进其策略与轨迹，不再新增重复节点。
5. 比较固定策略与动态策略，按简单、复杂和无需检索三类分别报告结果，避免平均值掩盖复杂题退化。

### 验证与完成条件

- 测试覆盖三类问题、无法分类回退、空知识库、重排模型不可用、旧工作流配置兼容，以及任务 2 的处理顺序。
- 节点轨迹能解释“为何检索/跳过、取多少段、是否重排”。
- 冻结题集上同时检查证据召回、回答正确率、输入 token、检索耗时；复杂题所需证据丢失须作为失败记录。

## 任务 4：长对话结构化记忆（原计划改动 2）

实施记录：[任务 4 交付与验证](implementation/task-4.md)、[增量验收](implementation/task-4-followup.md)。默认关闭；完整 HTTP/浏览器验证和用户六题人工复核已完成。合并及测试部署进度见 [发布记录](implementation/task-4-rollout.md)。

### 通俗解释

对话很长时，给模型一张随时更新的“记事卡”，记住预算、目标和已确定事实；卡片写错或用户改口时，要能回看原话并纠正。

### 具体步骤

1. 找到现有会话历史、上下文截断和工作流状态的存储方式。设计会话级记忆记录，至少包含事实键、值、来源轮次、更新时间、状态（已确认/待确认）与版本；它必须受现有会话权限约束。
2. 新消息到来时，从用户明确表达中更新事实；冲突时新事实不得静默覆盖旧事实，要记录变更及来源。对指代不明的内容回查原始轮次，仍无法确认则让模型澄清。
3. 构造模型上下文时选取相关事实及近期原始消息，设定 token 预算。记忆来源与原始对话分别可追溯；清除记忆不删除原始聊天记录。
4. 增加查看、纠正和清除入口及受权限保护的 API。默认关闭新记忆策略；旧会话没有记忆记录时可以继续聊天。
5. 用多轮题比较原版历史策略与新策略，特别检查“预算从 3000 改为 4000”“第二款”指代及用户撤销条件的场景。

### 验证与完成条件

- 测试覆盖事实新增、修改、冲突、清除、跨会话隔离、历史回查和长对话预算。任何用户纠正都能在下一轮生效。
- 页面能显示事实及来源轮次；模型输入轨迹能证明只发送选中的事实和近期消息。
- 报告多轮任务正确率、事实遗漏/错误继承次数、平均输入 token 与费用。若省 token 但条件记错，不算优化成功。

## 任务 5：工具超时、重试与恢复（原计划改动 3）

### 通俗解释

办事时第二步暂时失败，不该把第一步重做一遍；如果第二步是“创建日程”，重试也不能创建两次。

### 具体步骤

1. 选择上游一个具体工具节点类型作为首版范围，梳理其调用、超时、异常、节点轨迹及工作流持久化机制。明确只读工具和有副作用工具的边界。
2. 配置超时时间、最多重试次数及可重试错误类型。仅对超时和暂时性错误重试；参数错误、权限错误和已明确失败的业务结果直接终止。每次尝试记录开始/结束时间、结果和错误类型。
3. 在现有执行状态中保存已完成步骤、失败步骤和输入快照，提供受权限保护的“从失败处继续”入口。恢复前核对应用/工作流版本与原运行一致；不一致时拒绝自动继续并要求新运行。
4. 对有副作用的工具要求工具侧支持幂等键或可核对的操作结果；若无法保证，超时后标记“结果未知”并等待人工确认，不自动重试。幂等键在一次原始运行及其恢复中保持稳定。
5. 在执行轨迹页显示每步状态、重试次数、错误与恢复来源。用受控测试工具注入成功、超时、暂时性失败和“写入已成功但响应丢失”。

### 验证与完成条件

- 自动测试覆盖重试上限、不可重试错误、恢复跳过已完成步骤、版本变化、并发重复恢复请求、同一幂等键及未知结果不自动重试。
- 故障注入报告给出任务完成率、重复副作用次数、平均恢复耗时和额外 token/费用；重复副作用次数必须为 0 才可宣称写入工具安全恢复。
- 旧工作流在关闭新设置时保持原有执行语义。

## 任务 6：按任务难度选择模型（原计划改动 4）

**2026-10-10 状态：** 已实现双模型路由、一次升级、未知计量和三组评测接口；受控测试及18次真实开发冒烟通过。正式开发/冻结集、人工评分、完整账单和部署未完成，不能报告成本优化；详见 [task-6.md](implementation/task-6.md)。

### 通俗解释

简单活交给便宜的模型，难题交给能力更强的模型；便宜模型答得不合格时升级，但两次调用的钱都要算进去。

### 具体步骤

1. 找到现有模型节点的模型配置、调用、流式响应、用量统计及错误处理边界。配置一个低成本模型和一个高能力模型，两者均由现有模型管理功能选择，不新建供应商接口。
2. 用确定性规则做首版路由：明确的简单抽取/分类选低成本模型；多证据比较、工具结果综合及未识别任务选高能力模型。记录匹配规则和所选模型；规则不读取用户不可见的敏感信息。
3. 为低成本模型定义可机器校验的升级条件，例如要求 JSON 格式却解析失败、必需字段缺失或引用 ID 不属于已提供证据。开放式答案的“质量差”不能凭单个模型自评自动升级；这些题由评测结果分析。
4. 升级时保留同一任务 ID 和轨迹，计入两次调用的 token、费用与总耗时。两模型都失败时返回明确错误，不伪装成功。配置默认关闭，旧模型节点行为不变。
5. 用固定单模型、始终高能力模型和路由策略做对照，按题型报告成功率、升级率、每成功任务费用与 P95 耗时。

### 验证与完成条件

- 测试覆盖简单/复杂/未知任务、低成本模型格式失败、升级成功/失败、流式结果、缺失用量及双模型费用求和。
- 轨迹中能看到选模原因、升级触发条件和实际两次用量；模型密钥不会出现在轨迹。
- 只有在任务正确率达到预先确定的可接受阈值，且每成功任务费用确实下降时，才报告“成本优化”。阈值在运行冻结集前写入评测配置，不能看结果后更改。

## 最终交付检查

1. 六项功能都能在固定源码版本的本地实例中演示，配置关闭时原版行为可复现。
2. 新增后端行为测试、前端类型检查及构建、仓库已有检查全部实际运行；每条失败均记录原因，不用“预计通过”代替证据。
3. 用冻结题集生成原版、各阶段及最终版报告。报告列出逐题原始结果、汇总指标、统计口径、实验配置和失败案例，不编造提升百分比。
4. 文档与简历材料区分上游能力和本人增量贡献；如对外发布衍生版本，核对并遵守仓库的 GPL-3.0 许可。
